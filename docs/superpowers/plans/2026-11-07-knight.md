# 骑士 (Knight) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the `KNIGHT` god role end to end, with the duel rules in the spec: backend, frontend and tests. This is PR 1 of 2; the gravekeeper is a later, separate plan.

**Architecture:**
- The duel is a day interrupt like 自爆. A new `KnightDuelService` is dispatched from `GameActionDispatcher`, the way `SelfDestructService` is.
- It reuses the existing building blocks:
  - the `daySkipVoting` flag, so the host gets only `進入夜晚`;
  - `DayRevealAdvancer.nextSubPhase`, for a dead sheriff's badge handover;
  - `WinConditionChecker`, for the win check.
- The duel state lives on `games` and lasts the whole game. It enforces "once per game" and drives the day banner.

**Tech Stack:** Kotlin, Spring Boot 4, JPA, Flyway, JUnit5, Mockito-Kotlin, AssertJ; Vue 3, TypeScript, Pinia, Vitest; Playwright with the real backend.

**Spec:** `docs/superpowers/specs/2026-11-07-knight-gravekeeper-design.md`. Read the Decision record (D1–D3) and the KNIGHT rules (K1–K9) first. Rule ids below refer to the spec. Ignore every GRAVEKEEPER part: that is the next plan.

## Global Constraints

- **Kotlin.**
  - No `!!` in `src/main`; use `?: error("...")` instead.
  - Every new `DomainEvent` subclass needs `@JsonTypeName("<ClassName>")`.
  - Every new review DTO variant needs `@JsonTypeName`.
- **Migration.**
  - The new migration is `V32__knight.sql`. Never edit V1–V31.
  - The SQL must run on Postgres and H2.
  - Tests use `ddl-auto: create-drop`, so the migration gets its own verification step (Task 1).
- **Names, verbatim.**
  - Role `KNIGHT`.
  - Action `KNIGHT_DUEL`.
  - Game-event type `KNIGHT_DUEL`.
  - Domain event `KnightDuel`.
  - Columns `rooms.has_knight`, `games.knight_duel_target_user_id`, `games.knight_duel_day`.
  - Run the `verify-enum-values` skill before writing any of these literals.
- **Duel window (K1, D1):**
  - Allowed only in `phase == DAY_DISCUSSION && subPhase == RESULT_REVEALED && !daySkipVoting`.
  - Every other phase and sub-phase is rejected, all sheriff-election sub-phases included.
- **Check order in the service:** window → actor exists → actor is `KNIGHT` → actor alive → duel unused → target valid.
  - The window comes first. During the campaign, last night's victims are still `alive` in the DB, so a dead knight must get the same rejection as a living one (Review Focus 1).
- **Tests.**
  - No new Spring test contexts: use `@SpringBootTest @ActiveProfiles("test")` only, with no `@MockBean`/`@SpyBean`.
  - Use portable SQL and JPQL.
- **Frontend.**

  - `en.ts` and `zh.ts` keep the same keys, and `i18nParity.test.ts` stays green.
  - Type-check with `npx vue-tsc -b`.
  - `npm run lint` and `npm run format:check` must be clean.
  - Every element a test reads has a `data-testid`.
- **E2E.**
  - `getByTestId` only.
  - No sleeps, no retry loops, no `test.skip`.
  - The `roles` list includes `WITCH` (the setupGame trap).
  - The new spec is listed in a `.github/workflows/ci.yml` shard.

## Review Focus

These are failure modes no single task's happy path covers. Each has its test in the named task.

1. **A night-1-killed knight tries to duel during the sheriff campaign.** Its death is not yet revealed, so it is still `alive` in the DB. It must get exactly the same rejection message as a living knight; otherwise the response reveals the death.
   - Test: Task 2, `night-killed knight in SPEECH gets the window rejection`.
2. **A duelled wolf holds the badge.** The badge must go through the normal handover. A copy of `SelfDestructService` would destroy it instead.
   - Test: Task 3, `duelled wolf sheriff hands the badge over, not destroyed`.
3. **A duel copied from self-destruct sets `selfDestructUserId`.** The banner would then say 自爆.
   - Test: Task 2, `duel does not touch self-destruct fields`.
4. **A mechanical wolf that learned 猎人 is duelled.** No shot may open: not at once, and not at the next night-init.
   - Test: Task 3, `duelled mech wolf with SHOOT gets no pending shot`.
5. **A page refresh after the duel.** The chip must stay hidden, so its visibility must come from server state (`knightDuelUsed`), not component memory.
   - Test: Task 6, `chip hidden when knightDuelUsed is true`.
