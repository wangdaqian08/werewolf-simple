## 0. 前置改造：把「游戏表现」和「充值」拆成两种数值（其他各项都依赖这一节）

> **第一步已完成（#187，2026-11-12）**：战绩分 = `GAME_REWARD` 流水之和，由 `GET /api/user/stats` 的 `score` 返回；界面上「積分」全部改名「金幣」，「我的戰績」显示战绩分，结算页显示「+N 戰績分」和「同時獲得 N 金幣」。0-1、0-2 均按推荐选项。第二步未开工。

### 现状（代码事实）

| 项目 | 现在的实现 |
|---|---|
| 余额 | 一个钱包 `wallets.balance`（`model/Economy.kt`），所有变动都走 `WalletService.debit/credit`，每次变动写一条 `credit_transactions` 流水 |
| 流水类型 | `CreditTxType { PURCHASE, GAME_REWARD, PERK_SPEND, REFUND, ADMIN_GRANT }`（`model/Enums.kt:79`） |
| 充值包 | 入门包 100◈ = $1.99；超值包 300+30◈ = $4.99；豪华包 700+100◈ = $9.99（`V19__credits_perks_payments.sql`） |
| 游戏奖励 | 只给有胜负的对局，结算在 `RewardSettlementService`；金额在 `application.yml` 的 `werewolf.rewards`：胜利方 20、失利的好人 5、失利的狼每活一天 4、警徽 +5、投中狼每天 +3 |
| 消费 | 首夜免死 30◈；点将卡（狼／神／民）各 20◈；两者都是「生效才扣，没生效游戏结束时退回」 |
| 战绩 | `UserStatsService`：胜率、阵营战绩、最近 20 局、「击败 x% 玩家」（至少 5 局才参与排名） |

**问题**：充值的◈和赢来的◈是同一个数，所以：
- 按余额排名 = 充值榜，不能反映打得好不好；
- 经济平衡没法算：玩家花的◈里，分不清哪些是钱买的、哪些是游戏赚的。

### 新概念

| | **战绩分**（游戏表现） | **金币 ◈**（可消费） |
|---|---|---|
| 来源 | 只能靠玩游戏：对局奖励 + 任务奖励 | 充值、管理员发放、对局奖励的一部分（见待确认 0-1） |
| 能不能花 | 不能，只增不减 | 能：首夜免死、点将卡 |
| 能不能买 | 不能 | 能 |
| 用途 | 排行榜、个人战绩页 | 买道具 |
| 退款去向 | 不涉及 | 退回金币 |

### 最小改动方案（分两步，第一步不改表）

**第一步：零迁移，靠现有流水算战绩分**
- 战绩分 = 该用户 `credit_transactions` 里 `type = 'GAME_REWARD'` 的 `amount` 之和。这些流水一直都有，历史数据直接可用。
- 新增一个只读查询 + 接口给排行榜和个人页用；钱包、结算、退款代码都**不动**。
- 前端文案：现在的「◈ 积分」改叫「金币」；新增「战绩分」展示。

**第二步：当金币奖励和战绩分需要不同的数额时再做**（第 4 项调价时大概率会需要）
- 例如：为了控制通胀，把每局给的金币从约 16 降到约 10，但不希望排行榜上的分数也跟着缩水。
- 做法：`game_players` 加一列 `score_earned INT NOT NULL DEFAULT 0`（新的 `V(n+1)` 迁移，历史行用 GAME_REWARD 流水回填），结算时同时写战绩分（按表现）和金币（按经济参数）。排行榜改为 `SUM(game_players.score_earned)`。
- 任务奖励（第 1 项）也走这两个口子：战绩分 +X，金币 +Y。

> 为什么不一开始就拆成两个钱包：金币的扣款、退款、Stripe 入账都已经在用 `wallets.balance`。战绩分不能花，就不需要钱包那套「原子扣款 + 不足拒绝」，只要一个只增的累加值，放在流水或 `game_players` 上就够了。

### 待确认
- **0-1** ✅ 已定：给，数额暂时与战绩分相同，第 4 项再校准。
- ~~**0-1**：玩游戏还给不给金币？~~
  - 推荐：**给**，但数额按第 4 项校准（约等于道具消费的 70%）。这样免费玩家也能偶尔用道具，常用道具的玩家需要充值。
  - 另一种：**不给**，金币只能充值获得，道具变成纯付费。
- **0-2** ✅ 已定：老用户的余额全部算作金币，不迁移。

## 1. 任务系统

### 我的理解
发牌后，系统按你拿到的身份随机给你分配任务（单局有效），比如「活到第 3 天」「每晚都查到狼」。本局达成就有额外奖励，没达成没有惩罚。

### 两个维度
- **游戏表现**：完成任务加战绩分，并记入排行榜。
- **充值**：任务奖励的金币也算进第 4 项的产出总量里，不能单独让免费产出变高。

### 方案要点
- **分配时机**：每位玩家确认身份（CONFIRM_ROLE）后，在身份卡上看到自己的任务；**任务私密**，赛后复盘公开。
- **数量**：每局每人 1 个（推荐，简单），或 1 个身份任务 + 1 个通用任务。
- **判定**：全部在后端结算，用 `game_events`、投票、夜间行动等现有数据判定（`RewardBreakdown` 已经在用同样的数据算警徽和投中狼），在 `RewardSettlementService.settle` 里一起结算，流水写一个新类型，例如 `TASK_REWARD`。
- **防刷**：至少 6 人的对局才发任务（与连胜奖励草案一致）；游戏取消不结算。

### 任务池（草案，难度决定奖励）

| 适用身份 | 任务 | 难度 |

## 2. 全员排行榜

> **已完成（#188，2026-11-12）**：大厅卡片底部显示「戰績分排行榜」，接口 `GET /api/user/leaderboard` 返回前 3 名和「我」的一行（只有昵称，不返回用户 ID）。已知限制：每次请求在内存里汇总排序全部玩家，玩家多了再加缓存；大厅里不自动刷新。

### 我的理解
把所有玩过游戏的人排名，显示前 3 名；如果当前玩家不在前 3，第 4 行显示他自己的名字和名次（共 4 行）；如果他就在前 3，只显示 3 行。当前玩家那一行用特殊字号和颜色标出。

### 两个维度
- **游戏表现**：排名**只看战绩分**（第 0 节），充值买不来名次。
- **充值**：不上榜。如果以后要「充值榜」，单独做，不和这个榜混在一起。

### 方案要点
- 后端接口：返回前 3 名 +「我」的名次和分数；名次在后端算（并列规则见 2-3），前端只负责显示。
- 数据：第一步用 `GAME_REWARD` 流水求和；第 0 节第二步完成后改为 `SUM(score_earned)`。不需要排行榜专用的表，玩家规模大了再考虑缓存。
- 没玩过对局（战绩分 0）的玩家：不上榜，第 4 行显示「暂无排名，完成一局即可上榜」。
- 当前玩家那一行：沿用 Ink & Paper 配色，用 `--red` 加粗，字号比其他行大一号。
- 位置：大厅（推荐）或「我的戰績」页，见 2-1。

## 4. 积分经济平衡（防通胀）

### 我的理解
现在玩游戏获得的积分多、消费的少，余额会越攒越多。目标：
1. 买道具（首夜免死、点将卡）要能明显消耗余额；
2. 用道具的玩家，一局赚到的大约是这局花掉的 70%，也就是用道具的人平均每局净亏约 30%，需要偶尔充值；
3. 不用道具的玩家照常拿奖励，不受这个比例影响。

### 两个维度
- **游戏表现**：战绩分只反映表现，**不参与**平衡（只增不减，不能花，不存在通胀问题）。
- **充值（金币）**：平衡只针对金币。产出 = 对局奖励 + 任务奖励 + 充值 + 管理员发放；消耗 = 道具（扣掉退款）。

### 现状估算（需要用线上数据核实）
- 每局平均金币产出约 15–18◈（赢 ~25、输的好人 ~5–8、输的狼 ~12，按胜率约 50% 估算）。
- 首夜免死 30◈，但**只有狼人首夜刀中你才扣**，好人被首刀的概率大约十分之一，所以实际每局平均只扣约 3◈。
- 点将卡 20◈，拿到对应阵营才扣，大部分能生效，实际每局约 15–20◈。
- 结论：不用道具的玩家每局净赚约 16◈，10 局后约 160◈，够买 5 次首夜免死。**首夜免死「不生效就退」让它几乎不消耗金币，这是通胀的主要原因。**

### 方案方向（选一个或组合）
- **A. 降低对局产出的金币**（需要第 0 节第二步，避免战绩分跟着缩水）：把每局金币产出降到「典型道具价 × 0.7」左右。
- **B. 让道具真的扣钱**：首夜免死改为「使用即扣、不退」，同时降价（例如 15◈）；或者先扣一笔不退的手续费（例如 5◈），剩下的仍然生效才扣。
- **C. 价格跟着平均收入走**：道具价 ≈ 1.5 局的平均金币产出，这样一次购买相当于「打了一局半白打」，有明显的消耗感。

推荐 **A + B**：A 控制产出，B 让首夜免死真的成为消耗；点将卡已经大多会生效，按第 3 项分档即可。

### 线上数据与决定（2026-11-14）

数据来自产品负责人本地 PC 上的线上库（迁移到 V32，即 v0.10.x）。时间范围 2026-10-03 到 11-07，共 22 局：11 局有胜负、11 局被取消；有胜负的局平均 11.2 人；50 名玩家拿过对局奖励，其中 44 名是访客；**0 笔充值**。

| 金币 | 数值 |
|---|---|
| 发出：对局奖励 | 1764（123 人次，每人每局平均 14.3、中位数 16；每局全桌平均 160） |
| 发出：管理员发放 | 241 |
| 道具扣款 / 退款 | 1220 / 1060（退款率 87%） |
| 道具净消耗 | **160，只占发出的 8%** |
| 余额 | 50 个钱包共 1845；中位数 20，p90 102，最多 141 |

道具退款发生在哪里（这是关键）：

| 道具 | 有胜负的对局 | 被取消的对局 | 没开局的房间 |
|---|---|---|---|
| 点将卡·神 | 5 扣钱 / 1 退款 | 9 退款 | 15 退款 |
| 点将卡·狼 | 3 扣钱 / 0 退款 | 4 退款 | 8 退款 |
| 点将卡·民 | – | 1 退款 | – |
| 首夜免死 | 0 扣钱 / 2 退款 | 4 退款 | 4 退款 |

- 48 笔退款里 45 笔（94%）来自没打完的局（没开局 27、取消 18），退款本身是对的。
- **打完的局里，点将卡 9 次有 8 次生效（89%）**，「大多会生效」的假设成立；低生效率是没打完的局拉低的。
- 首夜免死在打完的局里也是 0 次扣钱：它只在首夜被刀时扣，这是规则使然。
- 11 局取消的对局停在第 1、2、4、5 天，从开局到结束平均 4–6 天：玩家中途散场，对局一直挂着，直到后端重启时被取消（推断，待新任务调查确认）。
- 样本很小（打完的局 11 局，点将卡真扣 8 次），以下价格是起点，上线一个月后再拉一次数据复核。

**决定（2026-11-14，产品负责人）**
- 点将卡分档：民 10 / 神 25 / 狼 30，规则不变（第 3 项）。
- **首夜免死不改**：仍是「首夜被刀才扣、否则退」，价格 30。
- 每局金币奖励**暂时不降**：用新价格估算，用点将卡的玩家每局花 10–30◈、收入约 14◈；一个月后用新数据复核是否需要 A。
- 老玩家余额不动。
- 不做「先扣一笔不退的手续费」：没打完的局占多数，收手续费对玩家不公平。
- 新任务：对局进行中长时间没人操作时自动取消并退还道具（先调查再改）。

## 5. 功能狼点将卡（机械狼、黑狼王、白狼王）

### 我的理解
在狼／神／民三张阵营卡之外，单独列出功能狼卡：点将卡·机械狼、点将卡·黑狼王、点将卡·白狼王。**只有本局板子里有这个角色时才显示这张卡。**神职不单独做（已确认）。

### 两个维度
- **游戏表现**：同第 3 项，不影响战绩分。
- **充值**：最贵的一档（见第 3 项表），用金币付。

### 方案要点
- 新增 3 个 perk：`ROLE_PICK_MECHANICAL_WOLF`、`ROLE_PICK_BLACK_WOLF_KING`、`ROLE_PICK_WHITE_WOLF_KING`；`RolePickChoice` 枚举加 3 个值，`room_players` 上对应的约束要一起改（新迁移）。
- 选项列表由后端根据房间板子给出，前端 `RolePickPanel` 照着显示，不在前端判断「板子里有没有这个角色」。
- 发牌顺序：**先处理功能狼卡，再处理阵营卡**。同一张功能狼卡多人选 → 随机抽签（沿用现有规则）；没抽中的人退款，**不自动降级成狼人阵营卡**（见 5-2）。
- 房主改了板子、删掉了某个功能狼：已经选了这张卡的玩家要被重置为「未选择」并退款（参考现在改板子时的处理）。
- 其余沿用现有点将卡规则：一人只能选一张、生效才扣、游戏中私密、赛后复盘公开。

### 待确认
- **5-1**：每人仍然只能选一张卡（推荐），还是可以同时选「狼人阵营」+「白狼王」？
- **5-2**：抽签没抽中功能狼时，是退款，还是自动当作「点将卡·狼人」再参加一次抽签（差价退回）？
- **5-3**：以后新加的功能狼（例如狼美人）是否默认自动有对应点将卡？

## 6. 准备状态：显示谁没准备

> **已完成（#185，2026-11-12）**：选了 6-1 的座位标签方案（不列名字）：没准备的座位显示红色加粗「未準備」；身份确认阶段，房主看到每个座位「已確認／未確認」的两列列表。

### 我的理解
房间里现在只有「x/12 · n 人未准备」这样的数字，大家不知道具体是谁没准备，没法催。要能直接看到没准备的人。

### 现状
- 顶部是数字（`RoomView.vue:30-39`）。
- 座位其实已经有区别：准备好的座位是淡绿底（`slot-ready`），没准备的是灰底（`slot-waiting`）。但**只有颜色，没有文字**，差别很小，看不出来，色弱玩家也分不清。
- 后端 `RoomDto` 已经带每个人的准备状态，**这一项只改前端**。

### 两个维度
不涉及战绩分和金币，纯界面改动。

### 方案要点（推荐两个都做）
- 在「n 人未准备」下面列出名字：`未准备：3号 小王、7号 阿杰`。
- 没准备的座位上加一个小文字标签「未准备」（或者给已准备的座位加 ✓），不能只靠颜色。
- 房主自己不需要准备，不显示在列表里；已加入但没选座位的人，已经在「未入座」列表里，不重复显示。
- 需要 `data-testid`，E2E 用 testid 定位，不用文字匹配。

### 待确认
- **6-1** ✅ 只要座位标签（「未準備」），不列名字
